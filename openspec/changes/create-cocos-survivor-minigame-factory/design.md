## Context

This repository is currently an empty planning workspace for a batch of casual mini games. The target direction is a high-feedback 2D "割草" survivor-like game built with Cocos Creator, then reused as a small production factory for multiple absurd, fast-testing themes.

The first reference theme is "打工人割草老板". The project should optimize for quick playable validation before polish: short sessions, dense combat feedback, simple controls, rapid upgrades, and repeatable reskinning. Visual assets should use the dedicated image2 workflow when generated by AI, but the game must not depend on AI at runtime.

## Goals / Non-Goals

**Goals:**

- Build a Cocos Creator 2D survivor-like prototype with player movement, enemy waves, auto attacks, pickups, upgrades, damage, death, and restart.
- Make the game content configurable so a new theme can replace characters, enemies, weapons, waves, and UI assets without rewriting core gameplay.
- Establish a local asset pipeline that uses image2 to generate theme art, stores generated outputs under project asset folders, and imports processed assets into Cocos Creator.
- Keep the first implementation small enough to validate within one playable vertical slice.
- Leave room for WeChat/Douyin mini game packaging, but keep the first pass focused on the Cocos project and browser/editor preview.

**Non-Goals:**

- No multiplayer, account system, backend, leaderboard, payment, or live operations in the first version.
- No complex 3D gameplay or physics simulation.
- No full frame-by-frame animation pipeline in the first version; use simple sprites, Cocos animation, particles, flash, scale, and screen shake.
- No automatic publishing to mini game platforms during the proposal phase.

## Decisions

### Use Cocos Creator 2D as the game runtime

Cocos Creator is the main target because it maps well to mobile mini game deployment, 2D sprite workflows, prefab reuse, particles, and lightweight TypeScript gameplay modules. Phaser would be faster for a web-only prototype, and Unity would be stronger for 3D or broader platform distribution, but Cocos is the best fit for WeChat/Douyin-style mini game production.

### Build one reusable survivor-like core first

The first implementation should be a single reusable core instead of several independent games. Core systems include player movement, enemy spawning, auto-targeting weapons, projectiles/area damage, pickups, upgrade selection, game timer, pause/restart, and basic HUD. This creates a stable loop that can be reskinned into many themes.

### Use configuration as the theme boundary

Theme-specific data should live in JSON or TypeScript config files. A theme config should reference player sprites, enemy prefabs/sprites, weapon definitions, upgrade options, wave schedules, drops, colors, and display names. Core gameplay code reads config and instantiates prefabs instead of hardcoding the "打工人" theme.

### Use image2 for source art, not runtime logic

image2 should generate visual source assets such as characters, enemies, weapons, skill icons, cover art, and concept sheets. Generated images should be saved into a project-local output folder, reviewed, cleaned/cropped as needed, then imported into the Cocos asset tree. API keys and provider settings must stay in the image2 skill's private settings and must not be committed.

### Prefer cheap animation and VFX over generated sprite sheets

For the first version, most entities can use one or two sprites plus Cocos-driven motion: flip by direction, bobbing, hit flash, scale pop, death burst, shadow, particles, damage numbers, and camera shake. This avoids the common AI sprite-sheet problem where frames drift in shape, perspective, and proportions.

## Risks / Trade-offs

- AI assets may look inconsistent across batches -> Mitigation: lock prompt style rules, generate per theme in small batches, and keep silhouette/proportion constraints in every prompt.
- Config-driven code can become too abstract too early -> Mitigation: support only the first vertical slice fields, then expand after the first theme works.
- Cocos mini game packaging details may differ by platform -> Mitigation: first validate in editor/browser preview, then add platform-specific packaging tasks after the core loop is stable.
- Too much visual polish can delay playable validation -> Mitigation: accept simple placeholder art for early gameplay, then replace with image2 assets after the loop feels good.
- Full generated animation may be unstable -> Mitigation: rely on Cocos animation, particles, and simple sprite transforms for the first release.

## Migration Plan

1. Scaffold a Cocos Creator project in this repository.
2. Implement the core survivor-like loop with placeholder assets.
3. Add the config schema and migrate the reference theme into config.
4. Generate or import the first theme assets and replace placeholders.
5. Verify the game in Cocos preview and adjust performance/feedback.
6. Keep rollback simple: retain placeholder assets and config defaults so the game can run even if generated theme assets are incomplete.
