# 16 移动端章节切换调试方法

## 目标

这份文档只解决一类高频问题：

- 洞府首页点了 `更换`，地图看起来没切
- 弹窗里章节详情变了，但首页主卡没变
- 明明改了状态代码，页面却总回到 `云栖竹谷`

目标不是泛泛而谈“怎么调前端”，而是固定这个项目里最有效的排查顺序，减少后续会话反复试错。

## 先用 HTTP，不要先在 file:// 上纠缠

调试首页章节切换时，优先启动本地服务：

```bash
npm run demo
```

默认地址：

```text
http://127.0.0.1:6273/
```

不要优先在下面这个地址上调交互：

```text
file:///.../demo/index.html
```

原因：

- `file://` 下 in-app browser 经常受 URL 安全策略影响
- 自动化点击、重载、状态回读都可能受限
- 很容易把“浏览器策略拦截”误判成“代码没生效”

结论：

- `file://` 适合肉眼看静态页面
- `http://127.0.0.1:6273/` 才适合真实调交互

## 这类问题的标准排查顺序

### 1. 先分清是哪一层没变

不要一上来就改 CSS。先确认到底是哪一层没变化：

1. 章节弹窗有没有打开
2. 弹窗里的 detail 章节有没有切
3. 首页标题有没有切
4. 首页主卡背景有没有切

如果弹窗 detail 已经切了，但首页标题和背景没切，说明问题不在资源，而在状态同步链路。

### 2. 看三个关键显示信号

章节切换是否真的生效，不要只看一处文字。至少同时看：

- 首页标题：`.mobile-run-title-row h2`
- 首页副标题：`.mobile-run-hero p`
- 首页卡面变量：`.mobile-run-card` 上的 `style` 和 `background-image`

本项目里，真正切成功的最小标准是：

- 标题变成目标章节名
- 副标题里的 Boss 名跟着变
- `--mobile-run-dashboard` 指向对应章节卡面图

例如切到 `玄石古阵` 时，应同时看到：

- `玄石古阵`
- `凡境 · 黑袍阵主`
- `mobile-run-dashboard-stone-array.webp`

### 3. 把交互链拆成两段查

这个项目里，“更换”交互不是一步，而是两段：

1. 首页 `更换` 按钮打开 `chapterQuickModal`
2. 弹窗里的章节按钮修改首页当前章节

因此必须分别验证：

- `open-chapter-modal` 是否真的打开了弹窗
- `preview-mobile-chapter` / `select-chapter` 是否真的改了首页当前章节

如果第一步正常、第二步异常，就不要继续怀疑按钮资源、遮挡或图没生成。

### 4. 优先怀疑“状态被回滚”，不是“点击没生效”

这次问题的真正根因不是按钮没触发，而是：

1. 弹窗章节 detail 状态已经切到了目标章节
2. 首页渲染前又执行了 `sanitizeMetaState()`
3. `sanitizeMetaState()` 根据 `unlocks.chapters` 把 `selected.chapterId` 强行修回默认章节

所以视觉表现是：

- 弹窗里像是切了
- 首页一回渲染就又变回 `云栖竹谷`

这类问题的排查原则：

- 不只看“谁在写状态”
- 还要看“谁在渲染前重置状态”

## 本次问题的实际根因

这次“更换没生效”是三个问题叠加：

### 1. 预览章节只改了 detail，没有即时重绘

最开始 `preview-mobile-chapter` 只写了：

- `homeState.mobileChapterDetailId = id`

但没有立即重绘弹窗，所以用户点章节列表时，弹窗内容都不一定马上变。

### 2. 首页当前章节和弹窗 detail 章节不是同一份状态

弹窗里的 detail 可以切到 `玄石古阵`，但首页仍读 `metaState.selected.chapterId`。

如果只改 detail，不改 selected，首页主卡不会切。

### 3. sanitizeMetaState 在每次渲染前把章节打回默认值

这是最关键的问题。

在移动端调试阶段虽然已经把：

- `isUnlocked("chapters", id)`  
改成了统一返回 `true`

但 `sanitizeMetaState()` 仍然用旧逻辑校验：

```js
if (!unlocks.chapters.includes(selected.chapterId)) {
  selected.chapterId = unlocks.chapters[0] || defaults.selected.chapterId;
}
```

结果是：

- 点击时章节确实改了
- 一渲染就又被打回默认章节

## 有效修复方式

### 1. 让弹窗章节按钮直接切首页章节

移动端章节弹窗里，点击章节列表不再只是预览 detail，而是直接：

- `setSelectedChapterForBuild(id)`
- 关闭弹窗
- 重绘首页

这样交互更直接，减少“点了章节还要再确认一次”的歧义。

### 2. 调试阶段让 sanitizeMetaState 也接受所有章节

如果本轮目标是“先看所有章节切换效果”，那就不能只改 `isUnlocked()`，还要同步改 `sanitizeMetaState()` 里的 `unlocks.chapters` 生成方式。

正确做法是基于 `metaConfig.chapters` 直接构造完整章节 ID 列表，避免渲染时把 `selected.chapterId` 修回默认值。

## 后续遇到同类问题时，固定这样查

### A. 先跑基础脚本

```bash
npm run config:check
npm run test:mobile
```

如果是图片资源相关，再补：

```bash
npm run assets:check
```

### B. 起本地服务

```bash
npm run demo
```

然后只在：

```text
http://127.0.0.1:6273/
```

下调交互。

### C. 按顺序验证

1. 点 `更换`，确认弹窗真的打开
2. 点目标章节，确认弹窗 detail 章节变了
3. 关闭后确认首页标题是否变了
4. 再确认首页背景变量是否变了

### D. 如果弹窗变了、首页没变，优先查这几类代码

- `demo/src/home/actions.js`
- `demo/src/home/controller.js`
- `demo/src/home/renderers.js`
- `demo/src/meta-store.js`

重点看：

- 点击事件有没有写入 `selected.chapterId`
- 渲染前有没有 `sanitize` / `normalize` / fallback
- 渲染读取的是不是同一份状态

## 不要再犯的误区

以下做法以后不要再重复：

- 在 `file://` 页面上花太久时间怀疑交互本身
- 只改 `isUnlocked()`，不改 `sanitizeMetaState()`
- 只看弹窗 detail，以为首页状态也已经切了
- 只看文案，不看 `mobile-run-card` 的背景变量
- 把“点击后又被回滚”误判成“按钮没生效”

## 最终验收口径

章节切换调通后，至少要满足：

1. 首页点 `更换` 能稳定打开弹窗
2. 弹窗里四个章节都能点击
3. 点击目标章节后，首页标题立即切换
4. 副标题里的 Boss 名同步切换
5. `--mobile-run-dashboard` 指向对应章节卡面图

只要这五项没同时满足，就不能算“章节切换已经修好”。
