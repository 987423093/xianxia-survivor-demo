# 14 合并流程与中断复盘

## 事件

在 `codex/mobile-shell-adaptation` 分支完成移动端壳层与图标化改造后，执行“合并到 `main`”时，用户体感耗时约 5 分钟，过程看起来像“卡住”。

实际结果：

- `main` 已成功合并，提交为 `ff2bea1`
- 合并内容本身没有失败
- 卡顿感主要来自合并前后的保护性流程，而不是 `git merge` 本身

## 直接原因

### 1. 工作区不是干净状态

合并前工作区存在与本次提交无关的改动：

- `demo/README.md`
- `docs/modules/README.md`
- `assets/generated/`
- `docs/modules/00-当前架构与开发约束.md`

为了避免把这些内容混入 `main`，执行了以下额外步骤：

1. 只挑选本次改动相关文件加入暂存区
2. 先提交当前分支
3. `stash --include-untracked` 收起无关改动
4. 切换到 `main`
5. 执行本地合并
6. 切回原分支
7. `stash pop` 恢复现场

这套流程是安全的，但明显拉长了用户等待时间。

### 2. 做了过度保守的收尾动作

这次请求的核心目标只是“把当前修改合并到 `main`”，但执行时还额外做了：

- 再次核对可归属文件范围
- 提交前后多轮状态检查
- 合并完成后恢复原分支和脏工作区

这些动作本身没有错，但对“快速完成 merge”这个目标来说过重。

### 3. 上一轮留下了常驻本地服务进程

为了前端截图验证，之前启动过 `npm run demo`。这个进程不会自行退出，虽然不是 `git` 合并的阻塞点，但会让会话看起来仍处于“忙碌”状态，降低用户对任务已完成的感知。

### 4. 合并完成时机晚于结果反馈时机

`main` 的本地 merge 实际完成很快，但在返回结果前仍在做工作区恢复和最后确认。用户在这个阶段中断了回合，导致“已完成但尚未反馈”的状态被感知为“卡住”。

## 结论

这次耗时不在 `git merge`，而在“保护脏工作区 + 过度收尾 + 常驻进程未及时收口”。

也就是说：

- 技术结果正确
- 流程效率偏低
- 用户感知不佳

## 后续执行规则

后续遇到“合并到 `main` / `dev` / 指定分支”类请求时，默认采用更直接的策略：

1. 先快速识别是否存在无关脏改动
2. 若存在，明确采用“临时 stash -> 合并 -> 恢复”最短安全路径
3. 不在 merge 流程里夹带前端预览、截图或额外验证进程
4. 合并完成后第一时间反馈结果，再做可选补充说明
5. 常驻本地服务在合并场景下必须及时收口，不挂在线程末尾

## 建议

如果后续该仓库经常出现“开发分支上混有无关本地改动”的情况，可以考虑补一个轻量流程约束：

- 合并前先把无关试验文件放到固定目录
- `assets/generated/` 这类候选产物默认不参与 merge
- 流程复盘文档统一放在 `docs/modules/`，不混入业务模块正文

这样可以降低类似问题重复发生的概率。
